# tests/stacks

교체 가능한 외부 스택(`services/stacks`) 테스트입니다. 자격증명 연결 관리와 주기 점검, 연결로만 자격증명을 읽는 규칙, 프로젝트별 분석 대상·저장소 대상과 저장 경합, 저장소 어댑터 계약을 봅니다.

## 주요 파일

| 파일 | 역할 |
|---|---|
| `test_connection_choices.py` | 프로젝트 관리자가 설정값·시크릿 없이 연결 이름 목록을 받고, 등록하지 않은 연결 이름은 저장되지 않는지 검사합니다. 품질검수 선택지(`purpose=caption_qc`)와 저장이 모델 연결만 받는지(저장소·MI 연결은 422 `connection_not_for_caption_qc`)도 봅니다. |
| `test_connection_watch.py` | 자격증명 연결의 주기 점검을 검사합니다. 아무도 화면을 보지 않을 때도 돌고 상태 전이를 연결 단위 이벤트로 기록하는지 봅니다. |
| `test_connection_address_guard.py` | 연결 주소 검사(메타데이터·루프백·점 없는 이름·http(s) 밖·사용자 정보 거절, 사설 대역 허용, 허용 목록)와 Bedrock이 키 없이 기본 자격증명 체인을 쓰지 않는지(점검은 실패, 품질검수 호출은 설정 없음) 검사합니다. |
| `test_connection_secret_reentry.py` | 저장된 시크릿이 있는 연결의 주소 키(엔드포인트·리전·API 주소)를 시크릿 없이 바꾸면 422 `secret_required_for_address_change`이고 설정과 시크릿이 그대로인지, 시크릿을 함께 보내거나 지우거나 시크릿이 없는 연결이면 통과하는지, 같은 주소 재전송과 주소가 아닌 값 수정은 시크릿 없이 통과하는지, 막힌 주소 사유가 먼저 나오는지, 거절된 수정은 감사 기록을 남기지 않는지 검사합니다. |
| `test_bedrock_keys_required.py` | Bedrock 연결이 생성·수정 뒤 두 키가 모두 남지 않으면 422 `bedrock_keys_required`이고 행을 만들거나 바꾸지 않는지, 두 키가 있으면 저장하고 같은 요청의 점검 결과를 남기는지, 이미 저장된 키 없는 연결의 점검이 AWS를 부르지 않고 실패인지, 다른 서비스는 키 없이 저장되는지 검사합니다. |
| `test_connection_update_audit.py` | 연결 수정 감사 기록이 바뀐 설정 키, 주소의 전후 값, 시크릿 교체 여부를 남기고 시크릿 값은 남기지 않는지 검사합니다. |
| `test_connections.py` | 자격증명 연결 관리(`/connections`)를 검사합니다. 연결은 기본 조직 한 곳에 속하고 시크릿은 쓰기 전용입니다. 저장하면 같은 요청에서 점검하고, 점검이 실패해도 저장은 남고 실패가 행에 기록됩니다. |
| `test_connections_only.py` | 자격증명을 등록한 연결에서만 읽는지 검사합니다. env에 NCP 키가 있어도 무시하는지, 연결을 고르지 않은 대상은 자격증명을 받지 않는지, 연결이 없으면 방식이 먼저 등록할 서비스를 싣는지, 선택지가 등록한 연결을 싣되 처음 값은 비워 두는지, 이전 원본 버킷을 영상의 연결로 읽는지 봅니다. |
| `test_mi_fake_mode_check.py` | 분석 연동이 꺼진 서버의 MI 연결 점검과 분석 대상 점검이 외부에 접속하지 않고 정상을 돌려주는지, 그 연결을 분석 대상으로 고를 수 있는지 검사합니다. 연동이 켜진 서버의 점검은 그대로 접속하는지도 봅니다. |
| `test_project_stack.py` | 프로젝트별 분석 대상을 검사합니다. 고른 MI 프로젝트 경로로 에셋을 등록하고 잡에 기록하는지, 폴링이 잡의 기록을 따르는지, 영상이 있는데 기록이 없어도 기본값으로 채우지 않고 409인지, 기록 없이는 등록 세 경로가 409인지, 첫 영상부터 잠기는지, 저장소 불일치·없는 MI 프로젝트·MI를 안 쓰는 방식이 422인지, 고른 연결을 못 지우는지, 점검 실패가 등록을 막고 다시 점검하면 풀리는지, 주기 점검 전이 기록을 봅니다. 실제 클라이언트는 `_request`만 기록용 가짜로 바꿉니다. |
| `test_storage_bucket_allowlist.py` | 저장소 연결의 허용 버킷 범위를 검사합니다. 선택지가 범위 안 버킷만 싣는지, 범위 밖 버킷 저장이 점검 객체를 쓰기 전에 422 `storage_bucket_not_allowed`인지, 범위 밖 버킷을 이미 기록한 프로젝트의 탐색·등록·폴더 등록·영상 등록이 422이고 마이그레이션 0108의 이행 뒤에는 동작하는지, 이행이 사람이 정한 목록과 버킷 없는 연결을 건드리지 않는지, 목록 형식 검사·정리·감사 기록, 프로젝트 관리자가 범위를 넓히지 못하는지 봅니다. |
| `test_allowed_bucket_in_use.py` | 프로젝트가 쓰는 버킷을 허용 범위에서 빼는 연결 수정이 409 `allowed_bucket_in_use`와 막는 프로젝트 이름으로 거절되는지, 쓰지 않는 버킷·삭제한 프로젝트·이미 범위 밖이던 버킷은 막지 않는지, 이름 상한과 연결 삭제 거절의 같은 응답 꼴을 검사합니다. |
| `test_project_storage.py` | 프로젝트별 저장소 대상을 검사합니다. moto에 두 번째 버킷을 만들고 그 버킷의 연결을 고른 프로젝트와 기본 버킷 프로젝트를 나란히 두어, 업로드 서명(단일·멀티파트)·업로드 확인·변환·비식별화·재생본 출력·마스터·재생 소스·포스터·클립 썸네일·납품 패키지·문의 첨부가 각자 버킷과 연결의 키로 가는지, 버킷 기록이 없는 행을 어느 버킷으로도 서명하지 않는지, 기록 없이 등록 세 경로가 409인지(샷 검출은 저장소만), 첫 영상부터 잠기는지, 고른 연결을 못 지우는지, 잠겼는데 기록이 없는 프로젝트가 막힌 채로 남는지, MI 워크스페이스 연동 버킷과 다르면 422인지, 점검 다섯 항목·모든 출처 CORS 경고가 저장을 막지 않는지·없는 버킷 422·등록 직전 409·주기 점검 기록을 봅니다. 등록 시트가 프로젝트 버킷 하나만 보이고 다른 버킷의 탐색·등록·폴더 등록을 422 `storage_bucket_not_project`로 막는지도 봅니다. |
| `test_storage_cors_any_origin.py` | 저장소 점검의 CORS 판정을 검사합니다. 업로드 방법을 모든 출처(`*`)에 허용하는 규칙은 경고와 좁히는 방법을 싣고, 화면 출처를 적은 규칙은 정상이며, 규칙이 없으면 업로드가 막힌다는 경고이고, 업로드 방법이 없는 규칙은 판정에 쓰지 않는지 봅니다. |
| `test_stack_save_race.py` | 스택 선택 저장(저장소·분석 대상)과 첫 영상 등록의 경합. 영상 등록이 설정을 읽은 뒤 행을 쓰기 전에 멈춘 사이 다른 DB 세션의 저장이 들어오면, 저장이 그 영상을 기다린 뒤 409 잠김으로 끝나고 영상과 프로젝트가 같은 선택을 가리키는지 봅니다(두 DB 세션을 실제로 겹쳐 돌립니다). |
| `test_storage_contract.py` | 저장소 계약 테스트입니다. 어댑터마다 따로 쓰지 않고 한 세트를 파라미터로 돌립니다. |
| `test_ncp_copy.py` | NCP 어댑터의 복사가 멀티파트 기준을 넘는 객체를 UploadPartCopy로 나누고 내용과 ContentType을 그대로 두는지, 작은 객체는 CopyObject 한 번으로 복사하는지 검사합니다. |

## 설계 이유

폴더 규칙과 둘 이상에 걸친 파일의 위치는 [`../README.md`](../README.md)에 있습니다.
저장소 어댑터 계약은 어댑터마다 같은 묶음을 파라미터로 돌립니다.

## 의존성

- 픽스처(`client`·`admin_token`)는 상위 `tests/conftest.py`, 시드 헬퍼는 `tests/_helpers.py`에서 옵니다.
- 모듈 이름은 폴더가 달라도 전체에서 유일해야 합니다. 하위 폴더에 `__init__.py`를 두지 않기 때문입니다.

## 남은 일

- 없음. 파일을 더하면 위 표에 한 줄을 더합니다.
